# PHASE 4 SPEC (PostgreSQL edition): Payroll, Expenses and Tax

Prerequisite: Phase 3 gate G3 passed (pilot signed off) or at least merged and green, attendance periods lockable, leave/LOP data flowing into `attendance_period_summary`.
Binding companions: `CA_VALIDATION_KIT.md` (statutory rules, golden cases, parallel-run protocol), `DESIGN_SYSTEM.md` (all UI, PDFs, emails), earlier specs and rule files.
Goal: accurate, auditable, configurable, FAST payroll for the organization, proven by parallel runs against the current process and signed off by a CA, plus expenses, tax declarations and statutory outputs.

## 0. Non-negotiable principles
1. **Rules are data, engines are code.** Rates, ceilings, slabs, thresholds, form names and effective dates live in versioned, maker-checker-approved rule sets. Engines are pure functions that read them. A Finance Act or notification change = new rule version, no deployment.
2. **The agent must never invent statutory values.** Seed rule sets are `draft` + `CA_VERIFY` and cannot be activated in production until a CA-approved payload is entered. Tests use clearly synthetic rule sets (names starting `TEST_`), never real-looking numbers presented as official.
3. **Test oracle comes from outside the code.** Golden-case expected values are supplied by the CA/Finance (`CA_VALIDATION_KIT.md`), never generated by running the implementation.
4. **Immutability.** A locked run and its payslips never change. Corrections are adjustments/arrears in a later run, or a controlled unlock before publication.
5. **Segregation of duties.** Preparer, approver and locker are different people (configurable strictness, default strict). Salary revisions, rule activation and bank-file generation use maker-checker.
6. **Exact money.** Integer paise or `numeric(14,2)` in the database; `decimal.js`/bigint in code; explicit rounding per component. No JavaScript floats for money, ever.
7. **Speed.** Bulk-load, compute in pure functions, write in chunks. No per-employee queries inside the calculation loop. Targets in section 12.

## 1. Scope
In: legal entities and payroll settings; salary components, formula engine, structures, CTC breakup; employee salary (effective dated, maker-checker); revisions and arrears; payroll inputs (bonus, incentive, deductions, reimbursements, loans); statutory rules layer (PF, ESI, Professional Tax, LWF, TDS under Section 392 of the Income-tax Act 2025, gratuity accrual, optional bonus); run engine and console; payslips (immutable snapshots + PDF); bank advice files and payment confirmation import; expenses with approvals and payout; tax declarations and proofs; statutory outputs (data files/reports); payroll reports; YTD opening-balance import; parallel-run reconciliation tool; mobile payslips, declarations and expense claims.
Out: full and final settlement UI and gratuity payout (Phase 6; the engine supports `final` run type and gratuity calc function now), leave encashment payout flow, multi-entity consolidation, foreign currency, e-filing/e-TDS FVU submission (data exports and CA handoff only), perquisite valuation beyond configured components, DA/ESOP taxation, arrears relief u/s 89 beyond CA-configured handling (flag as manual).

## 2. Fixed decisions
| Topic | Decision |
|---|---|
| Money | `numeric(14,2)` columns; `decimal.js` in code; per-component rounding (`half_up`/`floor`/`ceil`, to rupee or paisa) |
| Formula engine | Own safe parser/evaluator (tokenizer + Pratt parser, whitelist of functions `min,max,round,floor,ceil,abs,if,slab,pct,clamp,days_in_month`), no `eval`/`Function`; dependency graph with topological order and cycle detection at save time; variables are component codes and system variables (see 4.2) |
| Calculation | Pure function `computePayslip(input) -> output`, versioned `ENGINE_VERSION`; no DB, no clock, no randomness |
| Rules layer | `statutory_rule_sets` (versioned, effective-dated, jurisdiction-scoped, Zod-validated payload, maker-checker, pinned in each run) |
| PDF | Pure-JS renderer (pdfmake or react-pdf; decide by benchmark, record ADR), embedded Inter with the rupee glyph, target >= 20 payslips/s per worker. No headless Chromium for bulk payslips |
| Jobs | BullMQ chunked jobs (100 employees per chunk), idempotent via `input_hash`, progress through SSE |
| Salary storage | Amounts as plain `numeric` columns protected by RLS, permission checks, step-up, audit and disk encryption (needed for DB-side reporting). Bank account, PAN, UAN, Aadhaar remain app-level encrypted. Read-only reporting role has no access to payroll tables except aggregate views. Record as an ADR (alternative: encrypt amounts and aggregate in workers) |
| Currency formatting | `Intl` `en-IN` grouping (e.g. 1,23,456.00), tabular numerals, negative amounts in parentheses on payslips |
| Form names | Labels come from rule data, not code, so renames never need a release |

Seeded roles: `accountant` (settings read, components/structures manage, inputs create, run create/calculate/review, reports), new `finance_head` (approve inputs/rules/salary, run approve, bank file, statutory, recon signoff, expense pay), `hr_manager` (inputs create/approve limited, salary view with step-up, tax verify), `payroll_auditor` (read-only all payroll + audit), `employee` (own payslips, declarations, expenses), `manager` (approve team expenses), `super_admin` (all but SoD still applies to own actions; unlock requires reason + second approver). ## 5. Calculation engine
### 5.1 `computePayslip(input)` contract
Input (all pre-loaded, immutable): employee snapshot (DOJ, exit date, location, state, employment type, age/gender if needed by rules), entity settings, salary assignment effective for the period (with mid-period revision segments), structure version, attendance summary (paid days, LOP days, weekly offs, holidays), approved inputs, loans due, YTD and opening balances, tax declaration (regime, verified items, previous employer), rule sets (PF, ESI, PT for the employee's state, LWF, TDS, bonus, labour-code wages), engine config.
Output: lines (earnings, deductions, employer contributions, reimbursements), gross, deductions, net, employer cost, per-line `rule_ref` (formula text or rule key+version), warnings and blockers, TDS computation block, YTD deltas, gratuity accrual (provision), `input_hash`.
Determinism: same input => byte-identical output. No clock, no DB.
### 5.2 Steps (order matters, documented in code)
1. **Eligibility and proration**: joiner/exit mid-period, paid days from the paid-days basis, LOP days (from `attendance_period_summary` + approved `lop_override` inputs), salary segments for mid-month revisions (compute each segment, then combine), zero-days handling.
2. **Earnings** from structure formulas in dependency order; apply proration per component flag; round per component.
3. **Inputs**: arrears (re-apply prior-period components with their statutory effect), bonus/incentive, reimbursements, adjustments.
4. **Statutory wage bases**: PF wages, ESI wages, gratuity wages, bonus wages. When `LABOUR_CODE_WAGES.enabled`, `statutory wages = sum(statutory_wage components) + max(0, excluded components - floor_pct * total remuneration)` (rule-driven; CA confirms formulation and which components are excluded).
5. **PF**: employee and employer shares per rule (ceiling vs actual-wage option, EPS/EPF split, EDLI, admin charges, VPF), non-contributory days for ECR.
6. **ESI**: eligibility on rule threshold, employee/employer shares, contribution-period continuity (eligibility sticks for the contribution period), rounding rule.
7. **PT / LWF**: state slab tables by gross, gender/month-specific rules, months of collection.
8. **Loans/advances**: EMI recovery, limits so net stays within policy; partial recovery/skip rules.
9. **TDS (Section 392)**: `computeTds` pure function: annual projection = YTD + opening balances + this month + projected remaining months (current salary run-rate plus known one-offs), regime-specific standard deduction, exemptions, verified declared deductions (old regime only if the rules say so), slab tax, rebate with marginal relief, surcharge with marginal relief, cess; TDS this month = (annual tax - TDS deducted to date) / remaining months, never negative, never recovering more than allowed by policy; previous-employer income handled. All numeric parameters from `TDS_IN` rule data. Regime-compare helper uses the same function for both regimes (employee calculator).
10. **Net and checks**: net = earnings + reimbursements - deductions; apply `negative_net_policy`; blockers (missing bank details, missing PAN where required, unapproved salary, locked attendance missing, expired rule set) vs warnings (large variance, zero paid days, first payroll, structure wages below the labour-code floor).
11. **Totals, YTD deltas, gratuity provision, hash.**
### 5.3 Formula engine requirements
Grammar: numbers, identifiers, `+ - * / %`, comparisons, `and/or/not`, function calls, parentheses. Hard limits (expression length, depth, node count) and evaluation timeout for safety. Errors point to the position. Save-time validation: unknown identifiers, cycles, type errors, division by zero test with sample values. Unit tests with 100+ expressions incl. malicious inputs (prototype access, huge numbers, recursion).

## 6. Run engine and state machine
```
DRAFT -> INPUTS_READY -> CALCULATING -> CALCULATED -> REVIEW -> APPROVED -> LOCKING -> LOCKED -> PUBLISHED -> PAID
 re-open: CALCULATED/REVIEW -> DRAFT (inputs changed)       cancel: before APPROVED
 unlock: LOCKED -> REVIEW only if not published and not PAID; needs payroll.run.unlock + reason + second approver; audited
 after PUBLISHED/PAID: no unlock; use an off-cycle/correction run or adjustments next month
```
Preconditions (checked by one guarded transition function with row lock): attendance period locked for the month; all inputs approved or explicitly excluded; rule sets active for the period; salary assignments approved; no unresolved blockers (or employees explicitly held); different users for create/approve/lock per SoD.
- **Inputs freeze**: `INPUTS_READY` snapshots inputs and settings; later input changes require re-opening.
- **Calculate**: job fan-out in chunks of 100; per chunk: bulk load (<= 8 queries), compute, upsert `payroll_employee_runs` (skip unchanged `input_hash`); progress events; failures per employee captured as `error` with details, run continues; resumable and idempotent. Recalculate only changed employees.
- **Review**: variance versus previous run (set-based SQL join on `payroll_employee_runs`/`payslips`), explain-payslip drill-down, hold/release employees, add inputs (re-open), notes; summary totals by component/department/location.
- **Approve**: by a different user, step-up auth, checks control totals (gross, net, statutory totals) shown and re-verified.
- **Lock**: state LOCKING; materialize `payslips` and `payslip_lines` in chunks (idempotent `ON CONFLICT DO NOTHING`), update `payroll_ytd`, mark inputs consumed, mark loan installments recovered, mark expense claims paid-via-payroll, compute `integrity_hash` per payslip and `run_hash` over all; verify counts and totals equal staged results; then atomically set LOCKED. Resume safely after failure.
- **Publish**: generate PDFs (queue, >= 20/s per worker), store in MinIO, make visible to employees, notify (no PDF attached by default).
- **Pay**: bank advice file generation (approved by checker, step-up, audited, signed one-time download), payment confirmation import updates `payment_status`.
- **Off-cycle/correction**: same engine with `run_type`, restricted inputs, linked to the original period; recalculates TDS for the year correctly.

## 7. Payslips
Immutable snapshot with integrity hash; employer-branded PDF per `DESIGN_SYSTEM.md` (deep-green header strip, logo, Inter, tabular numerals, Indian grouping, earnings/deductions two-column table, net pay in words, attendance block, YTD block, employer contributions optional, footer with company details and confidentiality note). Access: employee self (permission `payroll.payslip.view` self), HR/Finance per permission with audit. Served through short-lived signed URLs; list loads instantly (indexed, paginated). Re-issue (corrected PDF template, same data) allowed; data changes only via correction runs. Download and view audited.

## 8. Bank files
Template-driven (data supplied from the owner's bank spec): generic NEFT/RTGS CSV plus configurable column mapping, fixed-width option, header/footer, control totals. Validations before generation: IFSC format, account number rules, duplicate accounts, zero/negative amounts, held employees excluded, total equals approved net. Generation needs checker approval + step-up; file stored encrypted, checksum recorded, download audited (one-time URL); regeneration creates a new version with reason. Payment confirmation import (UTR, status) maps to payslips and flags failed/returned payments.

## 9. Expenses
Flow: employee creates claim (web/mobile with camera capture), items with bills; policy engine flags (over limit, missing bill, duplicate bill via hash + amount + date, weekend/holiday, category not allowed for grade); submit starts the `expense` workflow (Phase 2 engine): manager, then finance for amounts above a threshold; item-level approve/partial approve with comments; payout choice: via payroll (creates idempotent `payroll_inputs` of type reimbursement, taxable flag from category) or via a separate bank reimbursement file; claim closes with payout reference. Reports: by category/department/employee, pending approvals, pending payouts, policy violations. Optional later: OCR (interface only), mileage, per-diem, foreign currency.

## 10. Tax declarations and statutory outputs
- **Declarations** (labels follow the current rules; configurable): regime choice at the start of the year and changes within the allowed window, investment/deduction declarations from `deduction_catalog`, HRA details, previous-employer income, proof upload and verification (HR/Finance), reminders before the cut-off, locked after the final proof window. Employee **regime comparison calculator** (new vs old) using `computeTds`.
- **Outputs** (data and files for the CA/filing; no e-filing): PF ECR text file per the current EPFO specification (agent must obtain and cite the official format; mark unverified if unavailable), ESI contribution data, PT and LWF summaries, quarterly TDS return data (Form 138 equivalent) and annual certificate data (Form 130 equivalent for tax year 2026-27 onward; Form 16/24Q labels for FY 2025-26 data), challan reconciliation, YTD ledger per employee. Each output has totals reconciled against payslip lines and flags mismatches.
- Statutory due-date calendar (configurable) with reminders.

## 11. Mid-year go-live and parallel run
- **Opening balances import** (`payroll_opening_balances`): YTD earnings by component, deductions, TDS deducted so far, PF/ESI/PT YTD, previous-employer data, as of the last month paid under the old process. Validate, preview, confirm, revertable, reconciled.
- **Reconciliation tool**: import the current process output (CSV/XLSX), map columns to component codes, compare per employee per component with tolerance (default 1 rupee), auto-categorize likely causes (rounding, missing input, rule difference), workflow of explanations, summary (matching %, total variance, open items), cycle sign-off by CA and Finance. At least 2 consecutive cycles with zero unexplained differences (3 preferred) before cutover.
- **Cutover plan**: recommended start of a month (ask the CA about quarter boundaries for returns), freeze date, final old-process run, import opening balances, first live run with Finance and CA on standby, rollback = continue the old process for that cycle.

## 12. Performance requirements (the app must not lag)
- Calculation of 5,000 employees <= 5 minutes on the reference hardware, bounded memory; chunk size tuned by benchmark; bulk loads (no per-employee queries); rule sets and structures cached per run.
- Single-employee simulate/preview and CTC breakup <= 1 s p95.
- Payslip list and viewer p95 <= 300 ms (PDF pre-generated, signed URL). Payroll console page <= 4 queries; run summary and variance via set-based SQL; tables virtualized and paginated server-side (keyset).
- PDF generation >= 20 payslips/s per worker; 5,000 PDFs in <= 6 minutes with 1 worker, parallelizable.
- Lock/materialize 5,000 payslips (about 75,000 lines) <= 3 minutes.
- Payroll never blocks request handlers; progress via SSE; console remains responsive during calculation.
- `pnpm perf:baseline` extended with payroll scenarios (calculate, lock, publish, console, payslip view); no regression of earlier budgets; results in `docs/perf/`.

## 14. Notifications and audit
Notifications: payslip published, declaration reminders, proof rejected, expense status, approvals pending, run ready for approval, statutory due dates. ## 15. Testing requirements
- **Golden files (>= 50 CA-supplied cases)** under `tests/golden/payroll/*.json`: `{input, ruleSnapshot, expectedLines, expectedTotals, notes}`; scenarios listed in `CA_VALIDATION_KIT.md`. All must pass 100%. The agent may add synthetic structural tests but never creates expected numbers from its own code.
- **Property tests**: net = earnings - deductions; sum of lines = totals; recalculation is idempotent; engine deterministic; proration monotonic; PF/ESI never exceed rule caps; TDS never negative; rounding preserves totals; random salary revisions produce non-overlapping assignments.
- **Formula engine**: 100+ expression cases, cycle detection, safety limits and injection attempts.
- **Rules layer**: maker-checker, effective dating, overlapping versions rejected, pinned versions in runs, activation blocked without passing test cases.
- **Run engine**: state transitions (allowed and forbidden), preconditions, SoD enforcement, concurrent calculate/approve/lock/unlock attempts, resume after crash in CALCULATING and LOCKING, input consumed exactly once, expense paid exactly once, loan installment recovered exactly once, immutable trigger tests (payslips/lines), integrity hash verification, run hash.
- **Security**: RLS and composite-FK tests for every table; IDOR (employees only own payslips/declarations/claims; managers only team expenses); permission matrix extended; step-up on salary view/approve/bank file; salary access audited; reporting role cannot read payroll tables; bank file one-time URL; PII not in logs.
- **Statutory files**: ECR/ESI/TDS-data format tests against official samples where obtainable; control totals equal payslip lines.
- **Bank**: validation rules, control totals, duplicate detection, regeneration versioning.
- **Expenses**: policy flags, duplicate bills, partial approvals, payout via payroll exactly once.
- **Migration/recon**: opening balance import effects on TDS projection (golden cases), recon diff categorization and tolerance, revert import.
- **Performance**: 5,000-employee calculate/lock/publish timings and memory, PDF throughput, console p95, payslip view p95, query budgets and plan tests (no Seq Scan at scale), k6 mixed load (payroll running while 200 users use attendance/leave/dashboards stays within earlier budgets).
- **E2E**: full cycle in staging seed (structure -> salaries -> inputs -> calculate -> review -> approve by second user -> lock -> publish -> employee views payslip -> bank file -> statutory outputs), declaration + regime compare, expense claim to payroll payout, reconciliation flow; mobile: payslip view, declaration, expense capture.
- **DR test**: restore a backup, re-verify payslip integrity hashes and run hashes.

## 16. Acceptance criteria (Gate G4)
1. Golden-file tests pass 100%; the CA has signed the rule sets, golden cases and sample outputs in writing.
2. Parallel run: >= 2 consecutive cycles (3 preferred) with zero unexplained differences against the current process (tolerance as agreed), signed by CA and Finance in the recon tool.
3. Locked runs and payslips are immutable (triggers + tests); integrity and run hashes verify after backup/restore.
4. A statutory rate/slab/form-name change goes live by adding a rule version (maker-checker) with no code deployment; effective dating verified by tests.
5. SoD verified: preparer cannot approve; approver cannot lock (strict mode); maker cannot check; every action audited.
6. Performance targets in section 12 met on the production build with 5,000 employees; no regression of Phase 1-3 budgets while payroll runs.
7. Bank files validated against the bank's own checker or portal in a dry run; statutory outputs reconcile to payslip lines; Finance signs the payslip format and bank file.
8. Expenses: claim to payout flows tested end to end; no double payment possible.
9. Opening-balance import produces correct TDS projections for mid-year go-live (golden cases).
10. Docs and runbooks (run stuck, unlock procedure, rule change procedure, bank file regeneration, statutory due calendar, correction run, opening balance import, rollback) delivered; `pnpm verify` and CI green.
